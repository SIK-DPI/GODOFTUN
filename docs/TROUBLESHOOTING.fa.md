# عیب‌یابی GODOFTUN V1.0.0

[English](TROUBLESHOOTING.md) · [فارسی](TROUBLESHOOTING.fa.md) · [简体中文](TROUBLESHOOTING.zh-CN.md) · [Русский](TROUBLESHOOTING.ru.md)

[راهنمای اصلی](../README.fa.md) · [نصب](INSTALLATION.fa.md) · [تنظیمات](CONFIGURATION.fa.md) · [مدیریت](OPERATIONS.fa.md) · [کلودفلر](CLOUDFLARE.fa.md) · [امنیت](SECURITY.fa.md)

از اولین مرحلهٔ ناموفق و همان تونلی شروع کنید که مشکل دارد. نصب مجدد، تعویض گواهی یا راه‌اندازی دوبارهٔ همهٔ سرویس‌ها ممکن است علت اصلی را پنهان کند. این بررسی‌ها تضمین سرعت، پایداری یا عبور از محدودیت‌های شبکه نیستند.

در دستورهای زیر، به‌جای `TUNNEL_ID` شناسه‌ای را بگذارید که دستور `list` نمایش می‌دهد. در گزارش‌های GODOFTUN، نقش ایران `origin` و نقش سرور خارج `egress` است. عبارت «origin server» در کلودفلر به سرور HTTPS خارج اشاره می‌کند، نه نقش ایران در GODOFTUN.

## چند بررسی اولیه

```bash
sudo godoftunctl list
sudo godoftunctl status TUNNEL_ID
sudo godoftunctl health TUNNEL_ID
sudo godoftunctl ports TUNNEL_ID
sudo godoftunctl doctor TUNNEL_ID --offline
sudo godoftunctl doctor TUNNEL_ID --timeout 8
sudo journalctl -u godoftun@TUNNEL_ID --since "15 minutes ago" -n 120 --no-pager
```

Doctor را روی هر دو سرور اجرا کنید. دستور `ports` پورت‌های ثبت‌شده را نشان می‌دهد؛ این خروجی به‌تنهایی ثابت نمی‌کند که برنامه‌ای روی آن‌ها در حال گوش‌دادن است. دستورهای `status`، `health` و `test` مفیدند، اما فعال‌بودن سرویس یا احراز هویت اتصال تونل، جای تست واقعی آپلود و دانلود با کلاینت Xray را نمی‌گیرد. گزارش‌ها را پیش از ارسال بازبینی کنید.

## دستورهای Doctor و حدود نتیجهٔ آن

گزینه‌های زیر پس از شناسهٔ تونل پذیرفته می‌شوند. `scan` نام دیگری برای `doctor` است.

| گزینه | کاربرد |
|---|---|
| `--offline` | تنظیمات تونل انتخاب‌شده را بدون درخواست شبکه بررسی می‌کند. |
| `--endpoints HOST:PORT,...` | مقصدهای مشخص را آزمایش می‌کند؛ IP یا دامنه، از جمله `[IPv6]:PORT`. URL، بازهٔ IP، CIDR و بازهٔ پورت پذیرفته نمی‌شود. اگر پورت ننویسید، اولین پورت خارج در تنظیمات استفاده می‌شود. |
| `--timeout N` | زمان هر مرحله برحسب ثانیه؛ عدد صحیح ۱ تا ۲۰ و مقدار پیش‌فرض ۸. تلاش احراز هویت هسته نیز مهلت محدود دارد. این گزینه سقف زمان کل گزارش چندمقصدی نیست. |
| `--output FILE` | یک گزارش JSON پاک‌سازی‌شده با مجوز `0600` ایجاد می‌کند. پوشهٔ مقصد باید موجود باشد؛ فایل موجود بازنویسی نمی‌شود. |
| `--binary PATH` | مسیر فایل اجرایی سازگار GODOFTUN؛ پیش‌فرض `/usr/local/bin/godoftun`. مسیر `run.sh` را ندهید. |
| `--help` | راهنمای واقعی گزینه‌های ابزار را نمایش می‌دهد. |

برای نمونه، دو پورت دامنهٔ تنظیم‌شدهٔ خودتان را مقایسه کنید:

```bash
sudo godoftunctl doctor TUNNEL_ID --endpoints tunnel.example.com:443,tunnel.example.com:8443 --timeout 8
sudo godoftunctl doctor TUNNEL_ID --output /root/godoftun-TUNNEL_ID-report.json
```

فقط مقصدهایی را وارد کنید که قصد بررسی آن‌ها را دارید. Doctor هنگام تست یک مقصد، Host، SNI، مسیر و احراز هویت تنظیم‌شده را حفظ می‌کند و تنظیمات تونل را تغییر نمی‌دهد. تست یک IP مشخص، ابزار تشخیص است؛ به معنی پشتیبانی از استقرار مستقیم روی IP نیست. سقف گزارش ۱۶ مقصد آزمایش‌شده است و آدرس‌های حاصل از DNS هم در این سقف حساب می‌شوند. اگر دامنه پاسخ‌های زیادی دارد، مقدار `candidate_limit_reached` را بررسی کنید.

روی ایران، مقصدهای پیش‌فرض همان دامنه و پورت‌های خارج در تنظیمات‌اند. روی خارج، پیش‌فرض شامل HTTPS محلی روی `127.0.0.1` و لبهٔ کلودفلر است؛ هر دو فقط روی **اولین** پورت خارج. بقیهٔ پورت‌ها را صریحاً مشخص کنید.

| نتیجه | چه چیزی را نشان می‌دهد؟ |
|---|---|
| `configuration-checked-not-network-tested` | بررسی آفلاین تنظیمات موفق بوده؛ شبکه تست نشده است. کد خروج ۰. |
| `carrier-authenticated` | دست‌کم یک تلاش واقعی WSS/V1 احراز هویت شده و هیچ مرحلهٔ گزارش‌شده‌ای ناموفق نبوده است. کد خروج ۰. |
| `partial` | یک اتصال احراز هویت شده، اما مرحله یا مقصد دیگری ناموفق بوده است. کد خروج ۱. |
| `failed` | هیچ مقصدی احراز هویت نشده است. کد خروج ۱. |
| `configuration-error` | تنظیمات پذیرفته نشده، یا فایل ورودی/گزارش محلی قابل خواندن یا ایجاد امن نبوده است. کد خروج ۲. |

مرحلهٔ `actual-carrier` از هستهٔ واقعی برای اعتبارسنجی TLS، پروفایل مرورگر، تنظیم ECH/Fragment، ارتقای WebSocket و احراز هویت پرسش‌وپاسخ V1 استفاده می‌کند. این تست هیچ جریان داده‌ای به مقصد Xray باز نمی‌کند. به همین دلیل، مقدارهای `target_payload_tested` و `cdn_origin_policy_verified` در گزارش false هستند. مقصد پیشنهادی فقط کمترین زمان یک تلاش اتصال را داشته؛ این نتیجه، اندازه‌گیری سرعت انتقال یا پایداری نیست.

## نصب پیش از ساخت تونل متوقف می‌شود

نصاب به دسترسی root، Ubuntu یا Debian، systemd و معماری Linux amd64 یا arm64 نیاز دارد. برای فایل اجرایی داخل بسته، نصب Go روی سرور لازم نیست. ابزارها یا وابستگی‌های موجودنبوده ممکن است همچنان به مخزن بستهٔ قابل‌دسترسی نیاز داشته باشند. خطای دقیق ابزار یا بسته را بخوانید؛ نصاب یک Nginx نصب‌شده اما خراب را خودکار تعمیر نمی‌کند.

برای پیام `flock is required`، پیش‌نیاز `util-linux` توزیع را از مسیر معمول نگهداری سرورتان فراهم کنید. اگر پیام `Another GODOFTUN installation is running` آمد، تا پایان آن عملیات صبر کنید؛ قفل را حذف نکنید و نصب دومی آغاز نکنید.

در تعارض پورت، پیش از هر تغییری مالک پورت را مشخص کنید:

```bash
sudo ss -ltnp 'sport = :443'
sudo nginx -t
```

به‌جای `443` پورت اعلام‌شده در خطا را بگذارید. از نصاب یا ویرایشگر، پورت آزاد انتخاب کنید یا تغییر سرویس فعلی را هماهنگ کنید. خطای `nginx -t` ممکن است مربوط به سایت دیگری باشد؛ برای موفق‌شدن تست، سایت‌های نامرتبط را حذف نکنید. اگر دامنه در اختیار سایت Nginx دیگری است، برای تونل نام میزبان جداگانه در نظر بگیرید. بک‌اند WebSocket برنامهٔ Go باید روی loopback بماند. برای رفع خطای مقصد تونل جدید، ورودی Native Reverse موجود را تغییر ندهید؛ ورودی اختصاصی توضیح‌داده‌شده در [راهنمای نصب](INSTALLATION.fa.md) را ایجاد کنید.

## DNS به کلودفلر اشاره نمی‌کند

این نصاب می‌خواهد نام میزبان خارج **فقط** به آدرس‌های تأییدشدهٔ پروکسی کلودفلر تبدیل شود. رکورد DNS-only، وجود IP سرور اصلی در پاسخ A/AAAA، پاسخ قدیمی resolver یا ناموفق‌بودن دریافت فهرست رسمی IPهای کلودفلر می‌تواند بررسی اولیه را متوقف کند. دامنهٔ اتصال، SNI و Host وب‌سوکت باید یکسان باشند.

```bash
getent ahosts tunnel.example.com
timedatectl status
```

هر دو رکورد A و AAAA، نام میزبان انتخاب‌شده، روشن‌بودن Proxy و IP سرور اصلی ثبت‌شده در کلودفلر را بررسی کنید. پس از انتشار تغییر DNS، همان بررسی ناموفق را تکرار کنید. دریافت‌نشدن فهرست رسمی IPها به معنی ناموفق‌بودن تأیید است؛ به‌تنهایی اشتباه‌بودن رکورد را ثابت نمی‌کند. در اتصال ایران، دامنه را با IP سرور خارج جایگزین نکنید و بررسی پروکسی را دور نزنید. [راهنمای کلودفلر](CLOUDFLARE.fa.md) را ببینید.

پورت‌های HTTPS خارج که نصاب می‌پذیرد عبارت‌اند از `443`، `2053`، `2083`، `2087`، `2096` و `8443`. پورت کلاینت ایران، پورت HTTPS خارج، پورت loopback بک‌اند Go و پورت مقصد Xray کاربردهای متفاوتی دارند.

## مرحلهٔ ناموفق شبکه را پیدا کنید

| نشانه یا پیام | بررسی بعدی |
|---|---|
| `DNS lookup failed` | رکورد و دسترسی به resolver. برای این نام‌گشایی ناموفق، TLS آزمایش نشده است. |
| `[tcp-connect]` یا connection refused | شنوندهٔ انتخاب‌شده، آدرس/پورت آن و رد صریح اتصال در شبکه. تعویض گواهی، پورت TCP را باز نمی‌کند. |
| Timeout یا `deadline` | مرحلهٔ اعلام‌شده، مسیر، بار سرور، سلامت شنونده و قواعد مرتبط فایروال میزبان/ارائه‌دهنده. timeout به‌تنهایی فیلترینگ، خطای توکن یا مشکل گواهی را ثابت نمی‌کند. |
| `[tls-config]`، `[tls-handshake]`، `x509` یا fingerprint mismatch | منبع اعتماد، نام/انقضای گواهی، بخش درست مسیر TLS و در صورت استفاده، تطابق پین گواهی. |
| `[tls-alpn] expected http/1.1` | مقصد انتخاب‌شده و جلوی سرویس TLS. این اتصال به ارتقای WebSocket روی HTTP/1.1 نیاز دارد. |
| پاسخ `404` وب‌سوکت | مسیر خصوصی دقیق، Host، عبور هدرهای Authorization/Upgrade، توکن مشترک و ساعت. رد پیش‌احراز هویت نیز عمداً پاسخ ۴۰۴ می‌دهد. |
| `403` یا `429` | چالش، WAF، کنترل دسترسی یا محدودیت نرخ CDN برای همان مسیر. این پاسخ به معنی اثبات اشتباه‌بودن توکن نیست. |
| `502`، `503`، `504`، `525` یا `526` | آدرس/پورت مسیر کلودفلر به خارج، HTTPS و گواهی سرور اصلی، Nginx و سلامت بک‌اند loopback. کد وضعیت به‌تنهایی علت دقیق را مشخص نمی‌کند. |
| `expected challenge`، `egress rejected token` یا unsupported protocol version | سازگاری نسخه‌های V1 و تنظیمات احراز هویت دو طرف. موفقیت ارتقای WSS کافی نیست. |

تونل نمی‌تواند چالش تعاملی مرورگر را تکمیل کند. قواعد همان نام میزبان/مسیر و شواهد رویداد مربوط در کلودفلر را بررسی کنید؛ امنیت کل حساب یا فایروال سرور را خاموش نکنید. پاسخ‌دادن صفحهٔ عمومی پوششی در `/`، سالم‌بودن مسیر خصوصی تونل را ثابت نمی‌کند.

## TLS در یک بخش مسیر موفق و در بخش دیگر ناموفق است

اتصال TLS ایران به لبهٔ کلودفلر، از اتصال کلودفلر به HTTPS سرور خارج جداست. Doctor علاوه بر آن‌ها، HTTPS محلی سرور خارج را هم بررسی می‌کند. گواهی لبه نمی‌تواند نبودن، ناهماهنگی یا انقضای گواهی سرور اصلی را جبران کند. برای بررسی محلی گواهی Cloudflare Origin CA، بستهٔ CA متناسب با آن لازم است؛ این گواهی، گواهی عمومی مورد اعتماد معمول کلاینت‌ها نیست.

جفت گواهی و کلید، نام DNS، تاریخ اعتبار، دسترسی سرویس به فایل‌ها و سیاست CA یا fingerprint انتخاب‌شده را بررسی کنید. هسته دقیقاً یکی از این سه روش اعتماد را می‌خواهد: ریشه‌های سیستم، فایل CA مشخص یا پین گواهی. در روش پین، نام میزبان و بازهٔ اعتبار هم بررسی می‌شوند. اعتبارسنجی گواهی را فعال نگه دارید و برای اعتماد صحیح، [امنیت](SECURITY.fa.md) و [کلودفلر](CLOUDFLARE.fa.md) را ببینید.

ساعت هر دو سرور باید درست باشد. اختلاف بیش از پنج دقیقه می‌تواند حتی با توکن صحیح، پیش‌احراز هویت وب‌سوکت را رد کند. به‌جای ساخت مکرر توکن جدید، سرویس زمان موجود را بررسی کنید.

## ECH یا Fragment ناموفق است

ECH در حالت strict هم به تنظیم قابل‌استفادهٔ ECH در رکورد DNS HTTPS نیاز دارد و هم به پذیرش واقعی آن توسط سرور. دستور `godoftun -check-ech DOMAIN` فقط دریافت و قابل‌استفاده‌بودن تنظیم را بررسی می‌کند، نه پذیرش موفق طرف مقابل. مرحلهٔ actual-carrier در Doctor، دست‌دادن واقعی انتخاب‌شده را بررسی می‌کند.

ECH strict به TLS 1.3 نیاز دارد و با قطعه‌بندی ClientHello قابل ترکیب نیست. موفقیت TLS معمولی یا نام پروفایل مرورگر، مدرک موفقیت ECH نیست. Doctor در پروفایل‌های ECH/Fragment عمداً تست TLS معمولی را رد می‌کند؛ وضعیت skipped این مرحله طبیعی است. اگر سیاست اعتماد، پین گواهی باشد نیز بررسی جداگانهٔ مبتنی بر CA انجام نمی‌شود.

برای تشخیص، هر بار یک تنظیم را با `godoftunctl edit TUNNEL_ID` تغییر دهید، به‌روزرسانی تولیدشده برای طرف مقابل را هماهنگ کنید و Doctor را دوباره اجرا کنید. خاموش‌کردن ECH یک تغییر صریح پروفایل است؛ fallback خودکار وجود ندارد. Fragment مرز نوشتن‌های TCP مربوط به اولین ClientHello را عوض می‌کند و تجهیزات میانی می‌توانند این نوشتن‌ها را دوباره تجمیع کنند. هیچ‌یک، اتصال یا سرعت بالاتر را تضمین نمی‌کند.

## قطع اتصال، راه‌اندازی مجدد یا توزیع نامساوی ترافیک بین پورت‌ها

گزارش هر دو تونل و خروجی `health` را در یک بازهٔ زمانی مقایسه کنید. بررسی کنید آیا سرویس راه‌اندازی مجدد شده، نشست طرف مقابل بسته شده، سهمیه تمام شده یا مهلت شبکه به پایان رسیده است. راه‌اندازی مجدد CDN/جلوی سرویس و خطای اتصال، نشست جدید لازم دارد؛ اتصال دوباره، جریان TCP قبلی برنامه را حفظ نمی‌کند. اگر راه‌اندازی مجدد لازم شد، پس از تشخیص تونل و پذیرفتن احتمال قطع اتصال‌های آن، فقط `sudo godoftunctl restart TUNNEL_ID` را اجرا کنید.

چند پورت خارج با ترتیب اولویت تنظیم می‌شوند؛ این به معنی ترافیک برابر روی همهٔ پورت‌ها یا تجمیع خودکار پهنای باند نیست. هر پورت موردنظر خارج را با `--endpoints` آزمایش کنید. هر پورت کلاینت ایران را با کلاینت واقعی تست کنید و تخصیص پورت و سهمیهٔ همان مشتری را ببینید. چند پورت ایران می‌توانند متعلق به یک مشتری و دارای سهمیهٔ مشترک باشند.

در فشار منابع، مصرف واقعی حافظهٔ فرایند را با محدودیت بافرهای نگهداری‌شده در [تنظیمات](CONFIGURATION.fa.md) مقایسه کنید. بودجهٔ حافظه، سقف کامل RSS فرایند نیست. بالا‌بردن تعداد نشست/جریان بدون بررسی حافظه و سرویس مقصد می‌تواند مشکل را بیشتر کند.

## کد تغییر دوطرفه رد می‌شود یا فقط یک طرف تغییر کرده است

روی هر دو طرف، `sudo godoftunctl edit-show TUNNEL_ID` را برای مقایسهٔ تنظیمات غیرمحرمانه اجرا کنید. کدهای امضاشدهٔ ویرایشگر فعلی به جفت و جهت مشخصی تعلق دارند، پس از هفت روز منقضی می‌شوند و مقدار قبلی را بررسی می‌کنند. تغییر بعدی، تونل اشتباه، طرف اشتباه، خطای ساعت یا کد V3/3.x می‌تواند پیام `Invalid, stale, expired, or wrong-peer update code` ایجاد کند.

جفت درست را مشخص و اختلاف مقدارها را بررسی کنید؛ سپس از سرور مناسب یک تغییر تازهٔ V1 تولید و با `sudo godoftunctl edit-apply TUNNEL_ID` اعمال کنید. `apply-update` نام دیگر همین دستور است. متن کد را دست‌کاری نکنید، هویت جفت را عوض نکنید و اطلاعات محرمانه را در issue نگذارید. یک تغییر محلی ممکن است تا اعمال تغییر متناظر در طرف مقابل، ترافیک را قطع کند؛ [راهنمای مدیریت](OPERATIONS.fa.md) را دنبال کنید.

## مشتری مسدود شده یا مصرف نادرست به نظر می‌رسد

روی ایران اجرا کنید:

```bash
sudo godoftunctl usage TUNNEL_ID
sudo godoftunctl customers TUNNEL_ID
```

وضعیت‌های `disabled`، `exhausted`، `stopped`، `status stale`، `status unavailable` و `blocked` معنای یکسانی ندارند. فعال‌بودن مشتری، سهمیهٔ کل دورهٔ آن و سهمیهٔ کل دورهٔ تونل را بررسی کنید. آپلود و دانلود با هم حساب می‌شوند؛ `0` برای همان سهمیه یعنی نامحدود و هر GB برابر ۱٬۰۰۰٬۰۰۰٬۰۰۰ بایت است. تغییر سهمیه، مصرف قبلی را حفظ می‌کند؛ بنابراین سهمیهٔ جدید کمتر از مصرف ثبت‌شده، مشتری را آزاد نمی‌کند.

مدیر فقط در بازهٔ حدود پنج ثانیه از زمان تغییر فایل وضعیت، آن را تازه در نظر می‌گیرد. سرویس متوقف، گزارش قدیمی یا گزارش موجودنبوده، به معنی مصرف زندهٔ صفر نیست. پیام `The service did not acknowledge the new customer configuration` یعنی نسخهٔ تنظیم درخواستی تأیید نشده؛ پیش از تکرار، سرویس انتخاب‌شده و خطای حسابداری اعلام‌شده را بررسی کنید.

دفتر مصرف پایدار در `/var/lib/godoftun/TUNNEL_ID/access-state.json` است. خطاهایی مانند `access state unavailable; refusing to reset usage`، ناهماهنگی checksum، خصوصی‌نبودن مجوز فایل یا `access state already in use` نیازمند بررسی تنظیمات و فایل وضعیت متناظر، مالکیت/مجوز، فضای ذخیره‌سازی و فرایندهای تکراری‌اند. برای بالا‌آوردن سرویس، دفتر مصرف را حذف یا از نو ایجاد نکنید. نسخهٔ پشتیبان آن را نگه دارید و روش بازیابی [راهنمای مدیریت](OPERATIONS.fa.md) را دنبال کنید.

حسابداری، بایت‌های آپلود/دانلود سوکت را بدون قاب‌بندی و padding تونل اندازه می‌گیرد. رزرو پایدار ممکن است پس از crash تا ۶۴ KiB به‌ازای هر حساب فعال، مصرف محافظه‌کارانه نگه دارد؛ این شمارنده‌ها الزاماً با کل ترافیک کارت شبکه نزد ارائه‌دهنده برابر نیستند. صفرکردن مکرر وضعیت، حسابداری کل دوره را خراب می‌کند.

## ارتقا یا بازگردانی ناموفق است

پوشهٔ بازیابی اعلام‌شده در `/opt/godoftun/backups` را نگه دارید. اولین خطای ارتقا و نتیجهٔ بازگردانی را بخوانید. برگشت تنظیمات ثابت نمی‌کند که مسیر شبکه سالم است؛ وضعیت سرویس، Doctor و تست کلاینت واقعی را دوباره بررسی کنید.

فایل اجرایی و ابزارهای مدیریت مشترک‌اند، اما تنظیمات و سرویس هر تونل جداست. طبق [راهنمای مدیریت](OPERATIONS.fa.md)، دو سرور جفت و هر تونل تحت‌تأثیر را ارتقا دهید. پروفایل پشتیبانی‌نشده یا نصب 3.x می‌تواند تعویض فایل اجرایی مشترک را متوقف کند؛ این بررسی را دور نزنید و نسخه‌ها/کدهای جفت‌سازی را ترکیب نکنید.

اگر بازگردانی اعلام کرد به رسیدگی دستی نیاز دارد، فایل‌های اصلی و ناموفق را همراه دفتر مصرف فعلی حفظ کنید. گزارش مصرف قدیمی را روی دفتر جدید کپی نکنید و تنظیمات Nginx کل سرور را بدون بررسی برنگردانید. بازگردانی خودکار تا حد امکان فایل‌های مدیریت‌شده و وضعیت سرویس را بازیابی می‌کند؛ وابستگی‌های دریافت‌شده، حساب سرویس و گواهی‌های صادرشده ممکن است باقی بمانند. نصاب Xray را تغییر نمی‌دهد. نبودن فایل مصرف عمداً نصب تازه با مصرف صفر تلقی نمی‌شود.

## Doctor موفق است، اما کلاینت Xray کار نمی‌کند

باقی مسیر برنامه را به‌ترتیب بررسی کنید:

1. کلاینت به IP ایران و پورت مشتری خودش وصل می‌شود و پروتکل، اطلاعات احراز هویت، نوع انتقال و TLS آن با ورودی اختصاصی Xray خارج هماهنگ است.
2. مشتری فعال است و هم سهمیهٔ مشتری و هم سهمیهٔ تونل اجازهٔ ترافیک می‌دهند.
3. مقصد خارج واقعاً روی آدرس loopback و پورت تنظیم‌شده گوش می‌دهد و فهرست مجاز مقصدهای egress دقیقاً همان مقصد را شامل می‌شود.
4. ورودی Xray تنظیمات کلاینت را می‌پذیرد و مسیر خروجی/DNS آن کار می‌کند.
5. کلاینت واقعی آپلود و دانلود انجام می‌دهد؛ انتقال کوتاه و طولانی را روی هر پورت ورودی موردنظر تست کنید.

اتصال WSS بین دو سرور، پروتکل یا TLS ورودی Xray را خودکار تغییر نمی‌دهد. ورودی اختصاصی را از سرویس‌های موجود جدا نگه دارید. برای شکل مسیر، [نصب](INSTALLATION.fa.md) و برای نقش پورت‌ها، [تنظیمات](CONFIGURATION.fa.md) را ببینید.

## گزارش پشتیبانی بدون اطلاعات محرمانه

نسخهٔ هر دو طرف با `godoftun -version`، سیستم‌عامل/معماری، نقش دو تونل، مرحله و زمان UTC خطا، نقش پورت‌های مربوط، فعال‌بودن ECH/Fragment/MUX، آخرین تغییر مرتبط و بخش کوتاهی از گزارش همان تونل را ارائه کنید. نتیجه و مراحل Doctor و موفق/ناموفق‌بودن آپلود/دانلود کلاینت واقعی را هم بنویسید. برای مشکل حسابداری، وضعیت نمایش‌داده‌شده و سن گزارش را بفرستید، نه خود دفتر مصرف را.

Doctor اطلاعات محرمانهٔ شناخته‌شده را پاک‌سازی می‌کند، اما گزارش همچنان شامل آدرس مقصد، SNI، شناسهٔ تونل و جزئیات تشخیصی است. پیش از اشتراک‌گذاری آن را بازبینی کنید. توکن، هدر Authorization، مسیر خصوصی وب‌سوکت، کد جفت‌سازی/به‌روزرسانی، کلید خصوصی، خروجی/اطلاعات ورود مشتری، فایل کامل اجرا/تنظیمات و فایل‌های حسابداری را حذف کنید. کل پوشهٔ پشتیبان را پیوست نکنید. فایل موجود `--output` بازنویسی نمی‌شود؛ برای گزارش جدید نام خصوصی تازه‌ای انتخاب کنید. [امنیت](SECURITY.fa.md) و [محدودیت‌های اعتبارسنجی این انتشار](../VALIDATION.md) را ببینید.
