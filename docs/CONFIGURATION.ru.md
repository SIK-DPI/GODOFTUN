# Настройка — GODOFTUN V1.0.0

[English](CONFIGURATION.md) · [فارسی](CONFIGURATION.fa.md) · [简体中文](CONFIGURATION.zh-CN.md) · [Русский](CONFIGURATION.ru.md)

[Главная](../README.ru.md) · [Установка](INSTALLATION.ru.md) · [Cloudflare](CLOUDFLARE.ru.md) · [Эксплуатация](OPERATIONS.ru.md) · [Диагностика](TROUBLESHOOTING.ru.md) · [Безопасность](SECURITY.ru.md)

GODOFTUN V1.0.0 поддерживает один вариант развёртывания: домен зарубежного сервера с включённым прокси Cloudflare через WSS и прямой вход по IP и порту в Иране. Редактор не позволяет выбрать Arvan, прямое зарубежное подключение без прокси, домен на иранской стороне, HTTP/2 или XHTTP. Он не настраивает клиенты Xray, аутентификацию inbound, учётную запись Cloudflare или DNS-записи.

## Открытие редактора

Замените `TUNNEL_ID` на ID из вывода `list`. Выполняйте команды на сервере, настройки которого нужно посмотреть или изменить:

```bash
sudo godoftunctl list
sudo godoftunctl edit-show TUNNEL_ID
sudo godoftunctl edit TUNNEL_ID
```

`edit-show` показывает сохранённую конфигурацию, а не текущее состояние соединения. Токен скрыт. Редактор показывает старое и новое значения и запрашивает `Apply? y/n`; ответ по умолчанию — `n`. Затронутый работающий сервис может перезапуститься; остановленный останется остановленным. Пользуйтесь меню вместо ручной перезаписи `run.sh` и метаданных: редактор совместно проверяет связанные ограничения, порты и параметры второй стороны.

## Подключение и идентификация

| Параметр | Назначение и ограничения | Область действия |
|---|---|---|
| Отображаемое имя туннеля | Печатный текст до 120 байт UTF-8 без `=`. Внутренний ID и идентификатор пары не меняются. | Локально |
| IPv4 зарубежного сервера | Адрес origin-сервера для метаданных и проверок; иранский соединитель по-прежнему подключается к проксируемому домену. При переносе сервера обновите фактический origin в DNS самостоятельно. | Общий |
| IPv4 иранского сервера | Публичный адрес для клиентов. На клиентских устройствах он не обновляется автоматически. | Общий |
| Зарубежный домен | DNS-имя, например `tunnel.example.com`, без схемы, порта и пути. Все разрешённые адреса должны пройти проверку прокси Cloudflare. | Общий |
| Зарубежные HTTPS-порты | Неповторяющиеся порты из `443,2053,2083,2087,2096,8443`, разделённые запятыми; установщик предлагает `443`. | Общий |
| Входные порты Ирана | Прямые TCP-порты входа клиента по умолчанию. У остальных клиентов свои настройки портов. Занятые и зарезервированные порты отклоняются. | Общие метаданные; слушатели меняются в Иране |
| Путь WebSocket туннеля | `/`, затем 15–511 букв, цифр, символов `/`, `_` или `-`. Создаётся при установке и должен совпадать на обеих сторонах. | Общий |
| Порт зарубежного Xray inbound | Уже работающая выделенная TCP-цель на `127.0.0.1` зарубежного сервера. Редактор проверяет конфликты; порт 80 оставлен для проверки сертификатов. | Общий |
| Смена общего секрета туннеля | Создаёт новый случайный токен, не показывая старый. Сразу согласуйте обновление второй стороны. | Общий |
| Файлы сертификата и закрытого ключа | Абсолютные пути к существующим файлам управляемого зарубежного сайта Nginx. Сертификат должен действовать, покрывать домен и соответствовать ключу. В этой редакции у Ирана нет публичного TLS-сайта. | Локально за рубежом |

Номера портов — 1–65535, с дополнительными проверками Cloudflare, принадлежности и слушателей. Не используйте закрытый backend-порт или целевой порт туннеля как публичный вход. При смене зарубежного домена на зарубежном сервере нужны соответствующие файлы сертификата: редактор не выпускает замену скрытно и не переписывает посторонние сайты Nginx.

## MUX, padding и ресурсы

| Параметр | Значение при новой установке | Диапазон редактора |
|---|---|---|
| MUX | `on` | `on` или `off`; общий |
| Интенсивность padding | `0.22`, передаётся в коде сопряжения | Конечное число от `0` до `1`; общий |
| Минимум сессий | `2`; `1`, если максимум равен `1` | `1`–`64`, не выше максимума; только Иран |
| Максимум сессий | `8` с MUX; без MUX предлагается `32` | `1`–`64`; только Иран |
| Максимум потоков | По таблице RAM ниже | `1`–`65,536`; локально |
| Потоков на сессию | `512` | `1`–`512`; локально |
| Общий бюджет удерживаемых буферов | По таблице RAM ниже | `16`–`1,048,576` MiB; локально |
| Удерживаемая память на поток | `2,048` KiB | `64`–`1,048,576` KiB; локально |
| Тайм-аут записи в туннель | `10s` | Целые секунды `1s`–`60s`; локально |
| Тайм-аут записи клиенту/цели | `0` | `0` отключает; иначе целые секунды `1s`–`300s`; локально |

Установщик выбирает ограничения отдельно на каждом сервере по `/proc/meminfo`:

| Обнаруженная физическая RAM | Общий бюджет буферов | Максимум потоков |
|---|---:|---:|
| Менее 1,5 GiB | 256 MiB | 1,024 |
| От 1,5 до менее 4 GiB | 512 MiB | 2,048 |
| Не менее 4 GiB или RAM не определена | 1,024 MiB | 4,096 |

Это исходные настройки установки, а не гарантированная ёмкость. Сохранённые значения смотрите в `edit-show`. Резервные значения самого ядра — 512 MiB и 512 потоков; установщик заменяет эти два значения профилем RAM.

Общий бюджет должен вмещать бюджет одного потока и не менее 64 KiB на каждый разрешённый поток. Для увеличения числа потоков может потребоваться сначала увеличить память; для уменьшения памяти — сначала снизить лимит потоков. Бюджеты учитывают удерживаемые входные буферы и незавершённые записи, **а не общий RSS процесса**. Другие выделения тоже расходуют RAM.

При включённом MUX несколько клиентских соединений используют общие сессии туннеля. Пул начинается с минимума и под нагрузкой может расти до максимума. Без MUX каждому клиентскому соединению нужна выделенная сессия; максимум сессий ограничивает число одновременных выделенных соединений, а минимум пула игнорируется. Отключение MUX обычно требует больше ресурсов.

Интенсивность padding — не процент полосы или длины данных: `0.22` не означает 22% дополнительного трафика. Вероятность активации и число байт не зависят от длины полезной нагрузки. `0` отключает padding; при нагрузке на очередь дополнение кадров данных подавляется. Увеличение значения может лишь повысить накладные расходы, не улучшив конкретный маршрут. В этой версии остаётся фиксированное окно управления потоком V1 в 512 KiB; адаптивного окна по RTT/потерям из 3.5 нет.

## TLS, ECH и Fragment

Эти настройки меняются в Иране, где создаётся исходящее TLS-соединение:

| Параметр | По умолчанию | Варианты |
|---|---|---|
| Профиль TLS-отпечатка | `chrome` | `chrome`, `firefox`, `ios` |
| Минимальная версия TLS | `1.3` | `1.3` либо явно выбранный режим совместимости `1.2` |
| ECH | `off` | `off`, `strict` |
| Разбиение ClientHello | `off` | `off`, `hello` |
| Размер фрагмента | `100-200` байт | `MIN-MAX`, где `16 ≤ MIN ≤ MAX ≤ 4096` |
| Задержка между фрагментами | `1-3ms` | `MIN-MAXms`, где `0 ≤ MIN ≤ MAX ≤ 20` |
| Доверенный CA bundle | Выбирается при установке | Абсолютный путь к существующему PEM bundle без пробелов |

Меню установки предлагает ECH off, строгий ECH либо ECH off с экспериментальным Fragment. Строгий ECH требует TLS 1.3 и отключённого Fragment. Прежде чем включить один конфликтующий режим, выключите другой. Если получение ECH-конфигурации не удалось или сервер не принял ECH, строгое соединение завершается ошибкой. Скрытого отката к обычному TLS нет.

Для поиска ECH выполняются запросы HTTPS DNS-записей через DoH в таком порядке:

1. `https://cloudflare-dns.com/dns-query`
2. `https://dns.google/dns-query`

Расширенный флаг ядра `-ech-doh` принимает список резолверов через запятую. Нужен HTTPS URL без учётных данных и фрагмента; перенаправления запрещены. Число переходов по DNS-псевдонимам и время запросов ограничены. В обычном редакторе поля резолвера нет. Этот механизм получает только ECH-конфигурацию и не заменяет системный резолвер для обычного определения адресов конечных узлов.

Установленный соединитель использует зарубежный домен как адрес назначения, SNI и WebSocket Host. Отдельного произвольного SNI для domain fronting в меню нет. Поиск ECH начинается с того же домена. Наличие ECH-записи не доказывает принятие ECH при реальном TLS-рукопожатии: используйте `godoftunctl doctor TUNNEL_ID`, затем проверьте клиентский трафик. См. [настройку Cloudflare](CLOUDFLARE.ru.md).

Fragment разбивает записи ClientHello. Он не меняет маршрутизацию, не делает недоступный IP доступным и не гарантирует устойчивость к фильтрации. Браузерные профили меняют характеристики TLS/HTTP-рукопожатия, но не превращают туннель в браузер и не гарантируют неразличимость.

Параметр `ca` в Иране проверяет **узел Cloudflare**. Отдельный `local_ca` — набор доверия для локальной диагностики TLS origin-сервера, а не CDN-узла. Можно предоставить CA bundle офлайн, но нельзя пропускать проверку сертификата. На уровне ядра для исходящего соединения нужен ровно один из `-ca`, `-system-ca`, `-fingerprint`. Управляемая установка использует `-ca`; отпечаток и системное хранилище не являются дополнительными пунктами установщика.

## Локальные и согласованные изменения

Общие поля: IP обоих серверов, зарубежный домен и порты, путь WebSocket, целевой порт, токен, MUX, padding и входные порты Ирана по умолчанию. Остальные параметры ресурсов, доверия и сертификатов локальны. Изменение отображаемого имени не требует синхронизации.

Для общего изменения:

1. Откройте `edit` на одной стороне, выберите поле и подтвердите изменение.
2. Безопасно передайте выданный конфиденциальный код соответствующей второй стороне.
3. Там выполните `sudo godoftunctl edit-apply TUNNEL_ID`, вставьте код в приглашение и проверьте изменение.
4. Проверьте обе стороны до следующего общего изменения. Пока значения расходятся, возможен временный разрыв связи.

Коды аутентифицируются HMAC, привязаны к идентификатору пары и противоположной роли и проверяют предыдущее значение. Они действуют семь дней и отклоняют устаревшие значения или не того партнёра; точные часы серверов важны. Первая синхронизация иранского IP/портов может заполнить отсутствующие зарубежные метаданные. Содержимое кода закодировано, **но не зашифровано**; код смены токена содержит новый секрет.

В этой версии `apply-update` — псевдоним `edit-apply`. Старые неподписанные/сырые форматы обновления и коды 3.x не принимаются. Установочный код из `peer-code` имеет другой формат и не является кодом редактора. При ошибке синхронизации сравните обе стороны и устраните указанное расхождение; не обходите проверки и не накладывайте поверх него новые несвязанные общие изменения.

## Клиенты, порты и накопительные квоты

Управление клиентами выполняется в Иране:

```bash
sudo godoftunctl customers TUNNEL_ID
sudo godoftunctl usage TUNNEL_ID
```

Установщик создаёт учётную запись `default` для исходных входных портов Ирана с неограниченной клиентской квотой. Отдельная общая квота туннеля по умолчанию равна `0`, тоже без ограничений. При добавлении клиента предлагается 100 GB: проверьте значение перед принятием. Позже клиенту можно назначить несколько портов, использующих одну квоту учётной записи.

Учёт привязан к **входному порту/учётной записи**, а не к аутентифицированному UUID Xray. Передача и приём суммируются. Считаются байты клиентского сокета в Иране без кадров и padding GODOFTUN. Это не счётчик биллинга ISP/CDN и не только размер прикладных файлов. Тот, кто может воспользоваться другим известным входом, может расходовать его квоту. Настройте настоящую аутентификацию на зарубежном приложении и при необходимости ограничьте либо отключите вход по умолчанию.

`1 GB = 1,000,000,000 bytes`. Дробное значение GB должно соответствовать целому числу байт. Управляющий инструмент принимает неотрицательную квоту до 9,000,000 GB. `0` означает отсутствие ограничения, но такой клиент всё равно ограничен конечной общей квотой туннеля. Достижение любого применимого лимита блокирует трафик; снижение лимита может закрыть текущие соединения.

Квоты — накопительные потолки, а не периодические пакеты. Если использовано 30 GB, после изменения лимита на 50 GB останется примерно 20 GB, а не ещё 50 GB. Переименование туннеля, смена портов, отключение/включение клиента, перезапуск и обычное обновление не сбрасывают расход. Команд ежемесячного продления, сброса расхода или удаления клиента нет.

Журнал расхода сначала сохраняет резерв байт, затем разрешает трафик. После аварийного завершения неиспользованный резерв может консервативно считаться израсходованным — до 64 KiB на активную учётную запись. Это защищает от недоучёта при перезапусках; не обещайте точного совпадения с внешним биллингом. Отсутствующее или повреждённое состояние учёта — ошибка, а не повод создать пустой журнал.

Отключение клиента закрывает доступ, сохраняя ID, квоту, счётчики и регистрацию портов. Повторное включение открывает доступ только при достаточной квоте. Сохранение клиентских настроек не запускает остановленный туннель. Смена портов сохраняет расход и отклоняет порты, зарегистрированные за другими клиентами или туннелями, даже отключёнными.

Экспорт клиента содержит сведения об endpoint, а не доступ к серверу, токены сопряжения или полные реквизиты Xray. Нужные клиентские реквизиты передавайте отдельно. Уже выданные файлы не меняются на устройствах автоматически: после смены endpoint экспортируйте и раздайте их заново. Полный список команд — в [Эксплуатации](OPERATIONS.ru.md); перед передачей файлов и диагностики прочитайте [Безопасность](SECURITY.ru.md).

## Расширенные флаги ядра

Справочник параметров вне управляемого редактора — `godoftun -h` установленного ядра. Значения по умолчанию: `dial-timeout=10s`, `auth-timeout=10s`, `open-timeout=15s`, `session-idle=90s`, `probe-timeout=15s`. Ядро разрешает 1–60 секунд для dial/auth/write, 1–120 секунд для open, более 30 секунд и до часа для session idle, положительное время probe до 60 секунд. Установщик включает статистику каждые пять секунд; само ядро по умолчанию её не пишет.

Не путайте ограничения флагов с диапазонами редактора: например, ядро принимает edge-write до часа, а редактор — до 300 секунд. Прямые изменения файла запуска могут нарушить управляемые проверки. Для повседневных изменений используйте редактор и фактически показанные им значения.
