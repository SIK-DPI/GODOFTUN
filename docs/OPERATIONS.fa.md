# مدیریت — GODOFTUN V1.0.0

[English](OPERATIONS.md) · [فارسی](OPERATIONS.fa.md) · [简体中文](OPERATIONS.zh-CN.md) · [Русский](OPERATIONS.ru.md)

[صفحهٔ اصلی](../README.fa.md) · [نصب](INSTALLATION.fa.md) · [تنظیمات](CONFIGURATION.fa.md) · [کلودفلر](CLOUDFLARE.fa.md) · [عیب‌یابی](TROUBLESHOOTING.fa.md) · [امنیت](SECURITY.fa.md)

دستورهای این صفحه برای اجرا روی سرور خودتان‌اند، نه گزارش انجام تست روی یک نصب واقعی. `TUNNEL_ID` و در صورت نیاز `CUSTOMER_ID` را با شناسهٔ واقعی جایگزین کنید. فرمان‌های مدیریت به دسترسی root نیاز دارند. پیش از نصب اولیه [نصب](INSTALLATION.fa.md) و پیش از تغییر مشترک یا سهمیه، [تنظیمات](CONFIGURATION.fa.md) را بخوانید.

## پیدا کردن تونل درست

```bash
sudo godoftunctl list
sudo godoftunctl status TUNNEL_ID
sudo godoftunctl health TUNNEL_ID
sudo godoftunctl edit-show TUNNEL_ID
```

نام نمایشی با شناسهٔ داخلی فرق دارد. نام سرویس محلی `godoftun@TUNNEL_ID`، پوشهٔ تنظیمات `/etc/godoftun/tunnels/TUNNEL_ID` و مسیر مصرف `/var/lib/godoftun/TUNNEL_ID` است. در اسکریپت‌های خودتان شناسه را صریح بنویسید. اگر شناسه ندهید، مدیر تونل تنها تونل موجود را انتخاب می‌کند یا برای چند تونل از شما انتخاب می‌خواهد.

## دستورهای نصب‌کننده

| آرگومان `bash ./GODOFTUN-V1.0.0.sh` | کارکرد |
|---|---|
| بدون آرگومان | منوی اصلی: نصب خارج، نصب ایران، مدیریت، انتقال فایل یا ارتقای V1 |
| `preview` یا `--preview` | نمایش منو بدون root، بررسی شبکه، نصب یا وضعیت زندهٔ ساختگی |
| `foreign` یا `egress` | نصب سمت خارج؛ نیازمند root |
| `iran` یا `origin` | نصب سمت ایران؛ نیازمند root و کد اتصال خارج |
| `manage` | مدیریت تونل‌های V1 پشتیبانی‌شده؛ نیازمند root |
| `upgrade` | ارتقای یک نصب V1 انتخاب‌شده و پشتیبانی‌شده؛ نیازمند root |
| `transfer-help` | نمایش راهنمای انتقال فایل |

نسخهٔ نصب‌شدهٔ اسکریپت در `/opt/godoftun/share/godoftun-easy.sh` است. برای ارتقا، نصب‌کنندهٔ انتشار تازه را بگیرید و بررسی کنید؛ اجرای دوبارهٔ کپی قدیمی، نسخهٔ جدید را دانلود نمی‌کند.

## فهرست کامل فرمان‌های `godoftunctl`

جز موارد مشخص‌شده، شکل دستور `sudo godoftunctl COMMAND TUNNEL_ID` است. `list` شناسه نمی‌خواهد و `help` راهنما را نشان می‌دهد. نمایش اطلاعات به‌تنهایی موفقیت ترافیک واقعی کاربر را ثابت نمی‌کند.

| فرمان | کاربرد |
|---|---|
| `list` | فهرست تونل‌های همین سرور |
| `status` | وضعیت کامل سرویس systemd |
| `health` | وضعیت سرویس، PID و restartها، منابع پردازش، آمار اجرای فعلی و listenerها |
| `monitor` | تازه‌سازی سلامت هر دو ثانیه؛ خروج با Ctrl+C |
| `logs` | نمایش ۱۰۰ خط آخر journal و ادامهٔ زنده؛ خروج با Ctrl+C |
| `start`، `stop`، `restart` | تغییر وضعیت اجرای فقط سرویس انتخاب‌شده |
| `config` | نمایش فرمان اجرای مدیریت‌شده؛ نصب معمول مسیر token را دارد، نه خود token داخل دستور |
| `info` | راهنمای endpoint مشتری و inbound |
| `ports` | پورت‌های ثبت‌شده؛ شامل رزروهای داخلی، نه فقط پورت باز عمومی |
| `peer-code` | نمایش کد محرمانهٔ نصب طرف مقابل در سرور خارج |
| `test` | بررسی سرویس و مسیر TLS تنظیم‌شده؛ نه تست کامل برنامه |
| `doctor`، `scan` | دو نام برای یک ابزار عیب‌یابی محدود؛ گزینه‌ها در ادامه آمده‌اند |
| `edit` | ورود به ویرایشگر کامل |
| `edit-show` | نمایش تنظیمات قابل‌ویرایش با token مخفی |
| `edit-ip` | پرسش دربارهٔ IP ایران یا خارج و ویرایش آن |
| `edit-ports` | پورت HTTPS خارج روی سرور خارج، یا پورت ورودی پیش‌فرض روی ایران |
| `edit-apply`، `apply-update` | اعمال کد ویرایش محرمانه و امضاشدهٔ V1؛ هر دو یک کار می‌کنند |
| `customers` | منوی مشتری‌ها روی ایران |
| `usage` | سهمیه، مصرف ثبت‌شده، مانده و وضعیت مشتری‌ها |
| `customer-add` | افزودن ورودی جدا برای مشتری و تهیهٔ راهنمای endpoint |
| `customer-quota` | تغییر سقف تجمعی مشتری بدون صفرکردن مصرف |
| `customer-disable`، `customer-enable` | تغییر دسترسی با حفظ حساب و مصرف |
| `customer-export` | ذخیره و نمایش فایل JSON endpoint مشتری |
| `customer-ports` | تغییر پورت‌های مستقیم یک مشتری با حفظ مصرف |
| `tunnel-quota` | تغییر سقف تجمعی مشترک کل تونل |
| `delete` | حذف یک تونل پس از واردکردن شناسهٔ دقیق؛ بخش حذف را بخوانید |
| `help` | نمایش راهنمای فرمان‌ها |

فرمان‌های مشتری موجود، `CUSTOMER_ID` را به‌عنوان آرگومان سوم می‌پذیرند؛ در غیر این صورت از شما انتخاب می‌خواهند. فهرست پورت و سهمیه در پرسش تعاملی گرفته می‌شود، نه آرگومان اضافهٔ مستندنشده. مثال:

```bash
sudo godoftunctl customer-export TUNNEL_ID CUSTOMER_ID
sudo godoftunctl customer-quota TUNNEL_ID CUSTOMER_ID
sudo godoftunctl customer-ports TUNNEL_ID CUSTOMER_ID
```

تغییر سهمیه/پورت پس از پاسخ به پرسش‌ها ذخیره می‌شود؛ فرض نکنید تمام کارهای مشتری، تأیید جداگانهٔ `Apply?` ویرایشگر را دارند. فرمان `customer-delete`، تمدید ماهانه یا صفرکردن مصرف وجود ندارد. پیش از تخصیص حجم، بخش سهمیه در [تنظیمات](CONFIGURATION.fa.md) را بخوانید.

## پایش و عیب‌یابی محدود

از `status` و `health` شروع کنید. Health آمار اجرای فعلی سرویس را می‌خواند، نه Session قدیمیِ اجرای قبلی. RSS ابزار سیستم با بودجهٔ بافر متفاوت است. `usage` وضعیت قدیمی/متوقف را مشخص می‌کند؛ snapshot قدیمی دادهٔ زنده نیست. `active` بودن سرویس، کارکرد احراز هویت Xray، عبور داده یا سرعت پایدار را ثابت نمی‌کند.

بررسی‌های زیر تنظیم تونل را تغییر نمی‌دهند. اولی آفلاین است؛ بقیه به endpoint تنظیم‌شده یا صریحاً انتخاب‌شده وصل می‌شوند:

```bash
sudo godoftunctl doctor TUNNEL_ID --offline
sudo godoftunctl doctor TUNNEL_ID --timeout 8
sudo godoftunctl doctor TUNNEL_ID --endpoints tunnel.example.com:443,tunnel.example.com:8443
sudo godoftunctl doctor TUNNEL_ID --output /root/godoftun-doctor.json
```

`tunnel.example.com` نمونهٔ مستندات است؛ فقط endpoint خودتان یا مقصدی را بگذارید که اجازهٔ تستش را دارید. `doctor`/`scan` حداکثر ۱۶ میزبان یا IP صریح را می‌پذیرد، نه بازهٔ آدرس. `--timeout` بین ۱ تا ۲۰ ثانیه و پیش‌فرض ۸ است؛ هر مرحله و مجموع probe هسته محدود می‌شوند. `--binary` برای انتخاب پیشرفتهٔ باینری هم‌نسخه است؛ پیش‌فرض `/usr/local/bin/godoftun` است، نه فایل اجرای `run.sh`.

`--offline` بدون درخواست شبکه تنظیم محلی را بررسی می‌کند و اتصال را تأیید نمی‌کند. موفقیت آنلاین به احراز هویت تازهٔ حامل نیاز دارد؛ ECH سخت‌گیرانه از handshake واقعی هسته استفاده می‌کند. حتی نتیجهٔ `carrier-authenticated` هم payload برنامه و رمز کلاینت را تست نکرده است. کد خروج ۰ یعنی حامل احرازشده یا بررسی آفلاین موفق، ۱ یعنی نتیجهٔ ناموفق عیب‌یابی و ۲ یعنی خطای تنظیمات یا گزارش.

`--output` فایل JSON خصوصی و پالایش‌شده می‌سازد و فایل موجود یا symlink را بازنویسی نمی‌کند؛ برای اجرای بعدی نام تازه انتخاب کنید. گزارش را پیش از اشتراک‌گذاری بازبینی کنید. لاگ خام، `config`، `info`، `edit-show` و اسکرین‌شات هنوز ممکن است آدرس، مسیر یا جزئیات عملیاتی داشته باشند. `peer-code`، فایل جفت‌شدن، کد ویرایش و backup محرمانه‌اند؛ آن‌ها را در issue عمومی نگذارید. [امنیت](SECURITY.fa.md) و [عیب‌یابی](TROUBLESHOOTING.fa.md) را ببینید.

## اعمال تغییر در طرف مقابل

روی یک طرف `edit` و روی دیگری `edit-apply` را استفاده کنید. کد چاپ‌شده را امن منتقل و داخل پرسش برنامه وارد کنید، نه در فرمان shell یا پیام عمومی. پیش از تغییر مشترک بعدی، تغییر قبلی را همگام کنید. شناسهٔ محلی دو طرف ممکن است متفاوت باشد؛ جفت واقعی را تشخیص دهید، نه صرفاً نام نمایشی شبیه.

کد هفت روز اعتبار دارد و مقدار قبلی، هویت جفت‌شدن و نقش مخالف را بررسی می‌کند. `apply-update` اکنون همان ویرایشگر امضاشده را اجرا می‌کند و راهی برای استفاده از قالب خام قدیمی نیست. `peer-code` مخصوص نصب اولیه است. تغییر دامنه/IP همچنان تغییر DNS و تنظیم دستگاه مشتری توسط شما را می‌خواهد؛ فایل تحویل‌شده به مشتری از راه دور عوض نمی‌شود. جزئیات در [تنظیمات](CONFIGURATION.fa.md) آمده است.

## انتقال نصب‌کننده وقتی دانلود محدود است

فایل کامل، هر دو معماری Linux را همراه دارد. فایل بررسی‌شده را از دستگاه مطمئن کپی کنید؛ برای دریافت خود باینری، ایران Go یا دسترسی GitHub لازم ندارد. IPهای مثال زیر برای مستندات رزرو شده‌اند؛ آدرس سرورهای خودتان را جایگزین کنید.

از دستگاه مطمئن، فایل انتشار را به ایران بفرستید:

```bash
scp ./GODOFTUN-V1.0.0.sh root@203.0.113.20:/root/GODOFTUN-V1.0.0.sh
```

یا روی ایران، کپی نصب‌شده را از خارج بگیرید:

```bash
scp root@198.51.100.10:/opt/godoftun/share/godoftun-easy.sh /root/GODOFTUN-V1.0.0.sh
```

فقط اگر کپی نصب‌شده واقعاً نصب‌کنندهٔ V1.0.0 موردنظر است، آن را با این نام ذخیره کنید. کلید میزبان SSH را بررسی و SHA-256 دریافتی را با اصل مطمئن مقایسه کنید، سپس اجرا کنید:

```bash
sha256sum /root/GODOFTUN-V1.0.0.sh
sudo bash /root/GODOFTUN-V1.0.0.sh iran
```

این روش **تحویل آفلاین فایل** است، نه تضمین نصب کاملاً بدون اینترنت. بسته‌های سیستم، DNS، بررسی گواهی و مسیر واقعی کلودفلر ممکن است هنوز شبکه بخواهند؛ وابستگی‌ها باید در دسترس باشند. نصب‌کننده بستهٔ PEM معتبر را در `/etc/godoftun/tunnels/TUNNEL_ID/ca-bundle.pem` یا مسیر مشترک `/etc/godoftun/ca-bundle.pem` می‌پذیرد؛ وگرنه بستهٔ CA سیستم را استفاده می‌کند یا نصب `ca-certificates` را امتحان می‌کند. فقط گواهی عمومی CA را از منبع مطمئن منتقل کنید، نه کلید خصوصی سرور. [نصب](INSTALLATION.fa.md) را ببینید.

## ارتقای نصب موجود V1

ارتقا برای نصب ثبت‌شدهٔ `GODOFTUN_V1_CF_WSS` است، نه مهاجرت از ۳.x. مشخصات ناسازگار ناوگان، حالت اتصال خارجِ پشتیبانی‌نشده یا باینری موجودِ ثبت‌نشده، تعویض فایل اجرایی مشترک را متوقف می‌کند. این محافظت‌ها را حذف نکنید و نصب ۳.x را با تغییر برچسب V1 جا نزنید.

1. توضیح تست انتشار تازه را بخوانید، نصب‌کنندهٔ قبلی و backup امن را نگه دارید و برای هر دو طرف زمان نگه‌داری در نظر بگیرید.
2. نصب‌کنندهٔ جدید را روی هر سرور با `upgrade` اجرا و تونل محلی درست را انتخاب کنید. بررسی DNS کلودفلر و تأیید نمایش‌داده‌شده را انجام دهید.
3. برای تمام تونل‌های هر دو سرور تکرار کنید. باینری و ابزار مدیریت مشترک‌اند، اما هر بار فقط تنظیم و سرویس تونل انتخاب‌شده ارتقا می‌یابد. سرویس‌های دیگر خودکار restart نمی‌شوند؛ اجرای بعدی آن‌ها از باینری مشترک جدید استفاده می‌کند.
4. `status`، `test` و `doctor` را بررسی و سپس با کلاینت واقعی ارسال/دریافت، چند پورت، سهمیه و وصل‌شدن دوباره را تست کنید. تست سرویس به‌تنهایی مسیر شبکه را تأیید نمی‌کند.

```bash
sudo bash ./GODOFTUN-V1.0.0.sh upgrade
```

تنظیمات پشتیبانی‌شده، گواهی، شناسه، سهمیه و مصرف حفظ می‌شوند و تونل متوقف روشن نمی‌شود. اگر تنظیم حسابداری وجود دارد ولی دفتر مصرف گم شده، ارتقا متوقف می‌شود و حجم تازه نمی‌دهد. V1 قدیمیِ پشتیبانی‌شده که هنوز حسابداری ندارد برای سقف اولیه سؤال می‌پرسد؛ اندازه‌گیری از همان ارتقا آغاز می‌شود، چون ترافیک گذشته قابل بازسازی نیست.

## بازگشت تغییر، backup و مصرف

تراکنش نصب/ارتقا، ویرایش تنظیمات و تغییر مشتری، نسخه‌های بازیابی محدود به کار خود را زیر `/opt/godoftun/backups/` نگه می‌دارند و مسیر همان عملیات را چاپ می‌کنند. در شکست، بازگرداندن فایل‌ها و وضعیت سرویسِ تغییرکرده تلاش می‌شود. اگر بازیابی امن تأیید نشود، ممکن است سرویس مربوط متوقف بماند و بررسی دستی لازم شود.

این فایل‌ها snapshot کامل و قابل‌جایگزینی کل سیستم نیستند. بازگشت ویرایش یا مشتری عمداً دفتر قدیمیِ ترافیک زنده را برنمی‌گرداند تا مصرف انجام‌شده بخشیده نشود. `access-state.json` قدیمی را روی دفتر فعال یا تازه‌تر کپی نکنید. خرابی دفتر، گم‌شدن فایل یا تأییدنشدن اعمال تنظیم باید بررسی شود؛ حذف فایل مصرف برای بالا آمدن سرویس، تضمین حفظ مصرف را از بین می‌برد.

فرمان مستندی به نام `godoftunctl restore` یا downgrade تک‌دستوری وجود ندارد. مطابق روش backup خودتان، نسخهٔ امن تنظیم مرتبط، وضعیت فعلی مصرف، انتشار هم‌نسخه و مدارک گواهی را نگه دارید. بازیابی دستی سازگار ممکن است توقف تونل و هماهنگی دو طرف را بخواهد. از backup واقعی همان عملیات و گزارش خطا استفاده کنید، نه یک دستور عمومی حدسی. Backup شامل رمز است و باید خصوصی بماند.

## توقف، غیرفعال‌کردن مشتری و حذف تونل

این سه کار متفاوت‌اند:

- `stop` فقط سرویس تونل را متوقف می‌کند؛ نصب، تنظیم و مصرف می‌مانند و `start` آن را برمی‌گرداند.
- `customer-disable` حساب را غیرفعال و دسترسی‌اش را قطع می‌کند، با حفظ هویت، مصرف، سهمیه و پورت ثبت‌شده. `customer-enable` مصرف را صفر نمی‌کند و سهمیهٔ تمام‌شده را دور نمی‌زند.
- `delete` یک تونل کامل را از مدیریت حذف می‌کند؛ حذف مشتری یا پاک‌کردن کل برنامه نیست.

شناسه را بررسی کنید و فقط وقتی قصد حذف همان تونل را دارید اجرا کنید:

```bash
sudo godoftunctl delete TUNNEL_ID
```

مدیر از شما تایپ شناسهٔ دقیق را می‌خواهد. سرویس را متوقف و غیرفعال می‌کند، تنظیم و وضعیت مصرف را به backup خصوصی `deleted-TUNNEL_ID-...` منتقل می‌کند و سایت مدیریت‌شدهٔ Nginx را فقط اگر تونل دیگری به آن ارجاع نداشته باشد برمی‌دارد. صحت تنظیم و reload Nginx بررسی می‌شود؛ در شکست، بازگشت تغییر تلاش می‌شود.

باینری مشترک، خود Nginx، سایر تونل‌ها، گواهی‌ها و قوانین firewall باقی می‌مانند. پورت بازِ بلااستفاده را خودتان بازبینی کنید؛ فرض نکنید حذف یک تونل بستن همهٔ پورت‌ها را امن می‌کند. حذف روی یک سرور، طرف مقابل، DNS یا دستگاه مشتری را حذف نمی‌کند. Backup باقی‌مانده دادهٔ قابل‌بازیابی است، نه ابزار بازیابی خودکار. برای رمزهای باقی‌مانده [امنیت](SECURITY.fa.md) و برای خطای حذف/بازیابی [عیب‌یابی](TROUBLESHOOTING.fa.md) را ببینید.
