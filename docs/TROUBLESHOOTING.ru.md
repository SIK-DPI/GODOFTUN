# Устранение неполадок GODOFTUN V1.0.0

[English](TROUBLESHOOTING.md) · [فارسی](TROUBLESHOOTING.fa.md) · [简体中文](TROUBLESHOOTING.zh-CN.md) · [Русский](TROUBLESHOOTING.ru.md)

[Обзор](../README.ru.md) · [Установка](INSTALLATION.ru.md) · [Настройки](CONFIGURATION.ru.md) · [Эксплуатация](OPERATIONS.ru.md) · [Cloudflare](CLOUDFLARE.ru.md) · [Безопасность](SECURITY.ru.md)

Начните с первого неудачного этапа проверки и конкретного туннеля. Переустановка, замена сертификатов или перезапуск всех служб могут скрыть исходную причину. Эти проверки не гарантируют определённую скорость, доступность или устойчивость к фильтрации сети.

В командах ниже замените `TUNNEL_ID` идентификатором из вывода `list`. В журналах GODOFTUN иранская сторона имеет роль `origin`, зарубежный сервер — `egress`. Термин «origin server» в Cloudflare обозначает зарубежный HTTPS-сервер, а не иранскую роль GODOFTUN.

## Соберите исходные сведения

```bash
sudo godoftunctl list
sudo godoftunctl status TUNNEL_ID
sudo godoftunctl health TUNNEL_ID
sudo godoftunctl ports TUNNEL_ID
sudo godoftunctl doctor TUNNEL_ID --offline
sudo godoftunctl doctor TUNNEL_ID --timeout 8
sudo journalctl -u godoftun@TUNNEL_ID --since "15 minutes ago" -n 120 --no-pager
```

Запустите Doctor на обоих серверах. Команда `ports` показывает зарегистрированные порты, но не подтверждает, что процесс их прослушивает. `status`, `health` и `test` полезны для проверки состояния, однако активная служба или прошедшее аутентификацию соединение туннеля не заменяют реальную загрузку и отправку данных клиентом Xray. Перед публикацией просмотрите журналы.

## Команды Doctor и границы проверки

Установленная управляющая команда принимает следующие параметры после идентификатора туннеля. `scan` — синоним `doctor`.

| Параметр | Значение |
|---|---|
| `--offline` | Разобрать выбранную конфигурацию без сетевых запросов. |
| `--endpoints HOST:PORT,...` | Проверить явно заданные адреса. Принимает IP или домены, включая `[IPv6]:PORT`; URL, CIDR, диапазоны адресов и портов не допускаются. Без номера порта используется первый зарубежный порт из конфигурации. |
| `--timeout N` | Время каждого этапа в секундах: целое число от 1 до 20, по умолчанию 8. Попытка аутентификации ядра также ограничена по времени. Это не общий предел времени для всего отчёта по нескольким адресам. |
| `--output FILE` | Создать JSON-отчёт с удалёнными известными секретами и правами `0600`. Родительский каталог должен существовать; существующий файл не перезаписывается. |
| `--binary PATH` | Использовать совместимый исполняемый файл GODOFTUN; по умолчанию `/usr/local/bin/godoftun`. Не указывайте `run.sh`. |
| `--help` | Показать актуальную справку диагностического инструмента. |

Например, сравните два порта настроенного домена:

```bash
sudo godoftunctl doctor TUNNEL_ID --endpoints tunnel.example.com:443,tunnel.example.com:8443 --timeout 8
sudo godoftunctl doctor TUNNEL_ID --output /root/godoftun-TUNNEL_ID-report.json
```

Указывайте только адреса, которые намерены проверить. При проверке кандидата Doctor сохраняет настроенные Host, SNI, путь и аутентификацию; конфигурация туннеля не меняется. Явно заданный IP служит для диагностики и не означает поддержку развёртывания с прямым подключением по IP. В отчёте проверяется не более 16 кандидатов, включая адреса, полученные через DNS. Если DNS возвращает много адресов, проверьте `candidate_limit_reached`.

На иранской стороне по умолчанию проверяются записи зарубежного домена и портов из конфигурации. На зарубежном сервере проверяются локальный HTTPS на `127.0.0.1` и узел Cloudflare; оба — только на **первом** настроенном зарубежном порту. Остальные порты задавайте явно.

| Результат | Что подтверждено |
|---|---|
| `configuration-checked-not-network-tested` | Автономная проверка конфигурации пройдена; сеть не проверялась. Код завершения 0. |
| `carrier-authenticated` | Хотя бы одна реальная попытка аутентификации WSS/V1 успешна, и ни один этап отчёта не завершился ошибкой. Код завершения 0. |
| `partial` | Одно соединение прошло аутентификацию, но другой этап или адрес не прошёл проверку. Код завершения 1. |
| `failed` | Ни один кандидат не прошёл аутентификацию. Код завершения 1. |
| `configuration-error` | Конфигурация отклонена либо не удалось прочитать локальный входной файл или безопасно создать отчёт. Код завершения 2. |

Этап `actual-carrier` использует настоящее ядро для проверки TLS, профиля браузера, ECH/Fragment, перехода на WebSocket и аутентификации V1 по схеме запрос–ответ. Поток к целевому Xray при этом не открывается. Поэтому поля `target_payload_tested` и `cdn_origin_policy_verified` в отчёте имеют значение false. Рекомендованный адрес выбран по минимальному времени одного соединения, а не по пропускной способности или надёжности.

## Установка останавливается до создания туннеля

Установщику нужны права root, Ubuntu или Debian, systemd и поддерживаемая архитектура Linux amd64 либо arm64. Для запуска исполняемого файла из пакета Go на сервере не требуется. Для отсутствующих инструментов и зависимостей могут понадобиться доступные репозитории пакетов. Прочитайте точную ошибку команды или пакета: установщик не исправляет автоматически уже установленный, но неисправный Nginx.

При сообщении `flock is required` обеспечьте наличие зависимости `util-linux` вашей системы обычным способом обслуживания сервера. При сообщении `Another GODOFTUN installation is running` дождитесь завершения текущей операции; не удаляйте блокировку и не запускайте вторую установку.

При конфликте портов сначала определите, кто занимает порт:

```bash
sudo ss -ltnp 'sport = :443'
sudo nginx -t
```

Замените `443` портом из сообщения об ошибке. Выберите свободный порт через установщик или редактор либо согласуйте изменение существующей службы. Ошибка `nginx -t` может относиться к другому сайту; не удаляйте посторонние сайты ради успешной проверки. Если домен уже принадлежит другому сайту Nginx, выделите туннелю отдельное имя хоста. Go-бэкенд WebSocket должен слушать только loopback. Не меняйте существующий inbound Native Reverse ради проверки цели нового туннеля; создайте отдельный inbound по [руководству установки](INSTALLATION.ru.md).

## DNS не возвращает адреса Cloudflare

Этот установщик требует, чтобы зарубежное имя хоста разрешалось **только** в проверенные адреса прокси Cloudflare. Запись DNS-only, IP исходного сервера в ответе A/AAAA, устаревший ответ резолвера или невозможность загрузить официальный список IP Cloudflare могут остановить предварительную проверку. Домен подключения, SNI и WebSocket Host должны совпадать.

```bash
getent ahosts tunnel.example.com
timedatectl status
```

Проверьте записи A и AAAA, выбранное имя хоста, включённый Proxy и адрес исходного сервера в Cloudflare. Дождитесь распространения изменений DNS и повторите неудачную проверку. Ошибка получения официального списка адресов означает, что проверка не завершена, но сама по себе не доказывает неверность DNS-записи. Не заменяйте домен иранского коннектора зарубежным IP и не отключайте проверку прокси. См. [Cloudflare](CLOUDFLARE.ru.md).

Установщик принимает зарубежные HTTPS-порты `443`, `2053`, `2083`, `2087`, `2096` и `8443`. Клиентские порты в Иране, зарубежные HTTPS-порты, loopback-порт Go-бэкенда и целевой порт Xray выполняют разные задачи.

## Найдите неудачный сетевой этап

| Симптом или сообщение | Что проверить дальше |
|---|---|
| `DNS lookup failed` | DNS-запись и доступность резолвера. Для этого неудачного разрешения имени TLS не проверялся. |
| `[tcp-connect]`, connection refused | Выбранный слушающий процесс, адрес/порт и явный отказ сети. Замена сертификата не открывает TCP-порт. |
| Timeout или `deadline` | Указанный этап, маршрут, нагрузку сервера, слушающий процесс и относящиеся к нему правила межсетевого экрана сервера/провайдера. Сам тайм-аут не устанавливает фильтрацию, ошибку токена или сертификата. |
| `[tls-config]`, `[tls-handshake]`, `x509`, fingerprint mismatch | Источник доверия, имя/срок действия сертификата, нужный участок TLS и закреплённый отпечаток, если он используется. |
| `[tls-alpn] expected http/1.1` | Выбранный адрес и TLS-фронтенд. Для этого соединения нужен переход на WebSocket через HTTP/1.1. |
| WebSocket `404` | Точный закрытый путь, Host, передачу заголовков Authorization/Upgrade, общий токен и часы. Отказ предварительной аутентификации также намеренно возвращает 404. |
| `403` или `429` | Проверку браузера, WAF, правила доступа или ограничения частоты CDN для данного маршрута. Это не доказывает ошибку токена. |
| `502`, `503`, `504`, `525` или `526` | Адрес/порт между Cloudflare и зарубежным сервером, HTTPS/сертификат исходного сервера, Nginx и loopback-бэкенд. Один код ответа не определяет точную причину. |
| `expected challenge`, `egress rejected token`, unsupported protocol version | Совместимость версий V1 и парную конфигурацию аутентификации. Успешного перехода на WSS недостаточно. |

Туннель не может пройти интерактивную проверку браузера. Изучите политику точного имени хоста/пути в Cloudflare и соответствующее событие; не отключайте защиту всей учётной записи или межсетевой экран сервера. Ответ публичной маскировочной страницы `/` не доказывает работу закрытого маршрута туннеля.

## TLS работает на одном участке и не работает на другом

TLS-соединение между Ираном и узлом Cloudflare отделено от соединения между Cloudflare и зарубежным HTTPS-сервером. Doctor дополнительно проверяет локальный HTTPS зарубежного сервера. Сертификат узла Cloudflare не исправляет отсутствующий, неверный или просроченный сертификат исходного сервера. Для локальной проверки сертификата Cloudflare Origin CA нужен соответствующий набор CA; это не обычный публичный сертификат, которому по умолчанию доверяют клиенты.

Проверьте соответствие сертификата и ключа, DNS-имя, срок действия, доступ службы к файлам и выбранную политику CA или отпечатка. Ядро требует ровно один способ доверия: системные корневые сертификаты, явный CA-файл или закреплённый отпечаток сертификата. При использовании отпечатка имя хоста и срок действия тоже проверяются. Оставьте проверку сертификатов включённой и настройте доверие по руководствам [безопасности](SECURITY.ru.md) и [Cloudflare](CLOUDFLARE.ru.md).

Время на обоих серверах должно быть правильным. Расхождение более пяти минут может привести к отказу предварительной аутентификации WebSocket даже при верном токене. Проверьте существующую службу времени вместо повторного создания токенов.

## Не работает ECH или Fragment

Строгий ECH требует и пригодной конфигурации ECH в DNS-записи HTTPS, и фактического принятия ECH сервером. `godoftun -check-ech DOMAIN` проверяет получение и пригодность конфигурации, но не успешное принятие другой стороной. Этап actual-carrier в Doctor проверяет выбранное реальное рукопожатие.

Строгий ECH требует TLS 1.3 и не может использоваться одновременно с фрагментацией ClientHello. Успешная обычная TLS-проверка или название профиля браузера не подтверждают работу ECH. Для профилей ECH/Fragment Doctor намеренно пропускает обычную TLS-проверку; такой статус skipped ожидаем. При закреплённом отпечатке сертификата отдельная проверка только через CA также пропускается.

Для диагностики меняйте по одному параметру через `godoftunctl edit TUNNEL_ID`, согласуйте применение сформированного обновления на другой стороне и повторите Doctor. Отключение ECH — явное изменение профиля, а не автоматический откат. Fragment меняет границы TCP-записей первого ClientHello; промежуточные устройства могут объединить их обратно. Ни один из этих режимов не гарантирует доступность или более высокую скорость.

## Обрывы, перезапуски или неравномерный трафик по портам

Сопоставьте журналы обоих туннелей и `health` за один и тот же период. Проверьте, перезапускалась ли служба, закрылась ли удалённая сессия, закончилась ли квота или истёк сетевой тайм-аут. Перезапуски CDN/фронтенда и ошибки соединения требуют новых сессий; повторное подключение не сохраняет прежний TCP-поток приложения. Если перезапуск нужен, сначала определите затронутый туннель и примите возможность разрыва его соединений, затем выполните только `sudo godoftunctl restart TUNNEL_ID`.

Несколько зарубежных портов задаются в порядке приоритета. Это не означает одинаковый трафик на каждом порту или автоматическое объединение пропускной способности. Проверьте каждый нужный зарубежный порт через `--endpoints`. Каждый клиентский порт в Иране проверьте настоящим клиентом и убедитесь в назначении порта и квоте конкретного клиента. Несколько иранских портов могут принадлежать одному клиенту и расходовать общую квоту.

При нехватке ресурсов сравните фактическую память процесса с ограничениями удерживаемых буферов из раздела [настроек](CONFIGURATION.ru.md). Заданный бюджет памяти не является пределом полного RSS процесса. Увеличение лимитов сессий/потоков без проверки памяти и целевой службы может усугубить сбои.

## Парное изменение отклонено или обновлена только одна сторона

Выполните `sudo godoftunctl edit-show TUNNEL_ID` с обеих сторон для сравнения несекретных настроек. Подписанные коды текущего редактора привязаны к конкретной паре и направлению, действуют семь дней и проверяют предыдущее значение. Последующее изменение, неверный туннель или сервер, ошибка времени либо код V3/3.x могут вызвать `Invalid, stale, expired, or wrong-peer update code`.

Подтвердите правильную пару, разберите различия, затем создайте свежее изменение V1 на нужном сервере и примените через `sudo godoftunctl edit-apply TUNNEL_ID`. `apply-update` — синоним этой команды. Не правьте закодированный текст, не меняйте идентичность пары и не публикуйте секреты в issue. Локальное изменение может прервать трафик до применения соответствующего изменения на другой стороне; следуйте [руководству эксплуатации](OPERATIONS.ru.md).

## Клиент заблокирован или расход кажется неверным

На иранской стороне выполните:

```bash
sudo godoftunctl usage TUNNEL_ID
sudo godoftunctl customers TUNNEL_ID
```

Статусы `disabled`, `exhausted`, `stopped`, `status stale`, `status unavailable` и `blocked` означают разные состояния. Проверьте, включён ли клиент, его накопительную квоту за весь срок использования и общую накопительную квоту туннеля. Отправка и получение суммируются; `0` означает отсутствие ограничения для этой квоты, а 1 GB равен 1 000 000 000 байт. Изменение квоты сохраняет прежний расход, поэтому новая квота ниже учтённого расхода не разблокирует клиента.

Менеджер считает файл состояния актуальным только примерно в пределах пяти секунд от времени его изменения. Остановленная служба, устаревший или отсутствующий снимок не означают текущий нулевой расход. Сообщение `The service did not acknowledge the new customer configuration` означает, что запрошенная версия конфигурации не подтверждена; перед повтором проверьте выбранную службу и указанную ошибку учёта.

Постоянный реестр расхода находится в `/var/lib/godoftun/TUNNEL_ID/access-state.json`. Ошибки `access state unavailable; refusing to reset usage`, несовпадение контрольной суммы, недостаточно закрытые права файла или `access state already in use` требуют проверки соответствующих конфигурации и состояния, владельца/прав, хранилища и дублирующихся процессов. Не удаляйте и не создавайте реестр заново ради запуска службы. Сохраните резервную копию и используйте процедуру восстановления из [руководства эксплуатации](OPERATIONS.ru.md).

Учёт измеряет отправленные и полученные байты сокетов без кадров туннеля и padding. После аварийного завершения постоянное резервирование может консервативно сохранить до 64 KiB расхода на каждую активную учётную запись; эти счётчики не обязаны совпадать с общим трафиком интерфейса у провайдера. Повторный сброс состояния нарушит накопительный учёт.

## Ошибка обновления или отката

Сохраните напечатанный каталог восстановления в `/opt/godoftun/backups`. Прочитайте первую ошибку обновления и результат отката. Восстановленная конфигурация не доказывает исправность сетевого пути; повторите проверку состояния, Doctor и тест реальным клиентом.

Исполняемый файл и управляющие инструменты общие, а конфигурации и службы туннелей отдельные. Обновите оба сервера пары и каждый затронутый туннель по [руководству эксплуатации](OPERATIONS.ru.md). Неподдерживаемые профили или установка 3.x могут заблокировать замену общего исполняемого файла; не обходите эту проверку и не смешивайте коды сопряжения или версии.

Если откат требует ручного вмешательства, сохраните исходные файлы, файлы после неудачной операции и текущий реестр расхода. Не заменяйте более новый реестр старым снимком использования и не восстанавливайте вслепую всю конфигурацию Nginx сервера. Автоматический откат по возможности возвращает управляемые файлы и состояние служб; загруженные зависимости, служебная учётная запись и выпущенные сертификаты могут остаться. Установщик не изменяет Xray. Отсутствие состояния учёта намеренно не считается новой установкой с нулевым расходом.

## Doctor успешен, но клиент Xray не работает

Проверьте оставшийся путь приложения по порядку:

1. Клиент использует IP Ирана и назначенный ему порт, а протокол, учётные данные, транспорт и TLS соответствуют отдельному inbound Xray на зарубежном сервере.
2. Клиент включён, и обе квоты — клиента и туннеля — разрешают передачу.
3. Зарубежная цель действительно слушает указанные loopback-адрес и порт, а список разрешённых целей egress содержит именно этот адрес назначения.
4. Inbound Xray принимает настройки клиента, его исходящее соединение и DNS работают.
5. Реальный клиент может отправлять и получать данные; проверьте короткие и длительные передачи на каждом нужном входном порту.

WSS-соединение GODOFTUN между серверами не меняет автоматически протокол или TLS-конфигурацию inbound Xray. Отдельный inbound должен оставаться независимым от существующих служб. Топология описана в [установке](INSTALLATION.ru.md), назначение портов — в [настройках](CONFIGURATION.ru.md).

## Подготовьте отчёт без секретов

Укажите `godoftun -version` обеих сторон, ОС/архитектуру, роли туннелей, неудачный этап и время UTC, назначение относящихся к проблеме портов, включены ли ECH/Fragment/MUX, последнее существенное изменение и короткие журналы затронутого туннеля. Приложите вердикт Doctor и результаты этапов, а также результат реальной отправки/загрузки клиентом. При проблеме учёта укажите отображаемое состояние и возраст снимка, а не сам реестр расхода.

Doctor удаляет известные секреты, но отчёт всё равно содержит адреса, SNI, ID туннеля и диагностические метаданные. Просмотрите его перед публикацией. Удалите токены, заголовки Authorization, закрытые пути WebSocket, коды сопряжения/обновления, закрытые ключи, клиентские экспорты/учётные данные, полные файлы запуска/конфигурации и файлы учёта. Не прикладывайте весь каталог резервной копии. `--output` не перезаписывает существующие файлы; для нового отчёта выберите новое закрытое имя файла. См. [безопасность](SECURITY.ru.md) и [границы проверки выпуска](../VALIDATION.md).
