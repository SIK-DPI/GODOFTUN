# نصب GODOFTUN V1.0.0

[English](INSTALLATION.md) · [简体中文](INSTALLATION.zh-CN.md) · [Русский](INSTALLATION.ru.md) · [صفحهٔ اصلی](../README.fa.md)

این راهنما برای نصب یک جفت تونل روی دو سرور است. ابتدا خارج و سپس ایران را نصب کنید. پیش از جایگزینی سرویس فعال، روی سرورهای جداگانه تست بگیرید.

## مسیر اتصال

```text
Client application
  -> Iran public IP and TCP entry port
  -> GODOFTUN origin
  -> foreign domain through Cloudflare WSS
  -> foreign Nginx and GODOFTUN egress
  -> dedicated application inbound on 127.0.0.1
```

حالت پشتیبانی‌شده ثابت است: پروکسی روشن کلودفلر برای خارج، WSS و ورودی مستقیم IP ایران. دامنهٔ ایران، آروان، خارج بدون پروکسی، HTTP/2 و XHTTP گزینهٔ نصب نیستند. این برنامه تونل TCP است، نه تونل UDP یا VPN کل دستگاه. برنامهٔ مقصد یا inbound پنل Xray همچنان به پروتکل، اطلاعات احراز هویت و تنظیم کلاینت خودش نیاز دارد. GODOFTUN همان محصول Cloudflare Tunnel یا `cloudflared` نیست.

## پیش از شروع

- دو سرور Ubuntu یا Debian دارای systemd، دسترسی root از طریق `sudo` و IPv4 عمومی داشته باشید. نصاب amd64/x86_64 و arm64/aarch64 را می‌پذیرد؛ سیستم ۳۲بیتی و نصب روی macOS پشتیبانی نمی‌شود.
- یک زیردامنهٔ اختصاصی خارج، مثلاً `tunnel.example.com`، مطابق [راهنمای کلودفلر](CLOUDFLARE.fa.md) آماده کنید. این نام فقط مثال است؛ دامنهٔ خودتان را جایگزین کنید.
- روی خارج یک inbound اختصاصی بسازید که روی `127.0.0.1` و یک پورت TCP آزاد گوش کند. پورت `18082` فقط زمانی درست است که واقعاً inbound را آنجا ساخته باشید. inbound نامرتبط پنل را تغییر ندهید.
- گواهی و کلید سرور خارج را آماده کنید یا مسیر چالش HTTP برای صدور خودکار Let's Encrypt را باز بگذارید. گواهی لبهٔ کلودفلر به‌تنهایی کافی نیست.
- برای دریافت ابزارهای کمبوددار به مخازن بسته‌های سیستم، برای تأیید پروکسی به API محدوده‌های IP کلودفلر و برای تونل به HTTPS خارج دسترسی لازم است. ECH به کشف DNS از طریق HTTPS هم نیاز دارد. انتقال آفلاین نصاب این نیازها را حذف نمی‌کند.
- ساعت دو سرور هماهنگ باشد و دسترسی SSH فعلی را هنگام تغییر فایروال حفظ کنید.

نصاب خانوادهٔ سیستم‌عامل را بررسی می‌کند، نه اینکه تک‌تک انتشارهای Ubuntu/Debian را تأیید کرده باشد. [دامنهٔ تست‌ها](../VALIDATION.md) را ببینید و از بسته‌های به‌روز سیستم‌عاملِ تحت پشتیبانی استفاده کنید. روی هیچ‌یک از سرورها کامپایلر Go لازم نیست.

## بررسی فایل دانلودشده

کل ZIP عمومی را استخراج کنید، وارد پوشهٔ `sik-dpi` شوید و فایل `SHA256SUMS` را کنار بقیهٔ فایل‌ها نگه دارید. روی لینوکس:

```bash
sha256sum -c SHA256SUMS
bash -n GODOFTUN-V1.0.0.sh
bash GODOFTUN-V1.0.0.sh preview
```

روی macOS دستور اول را با `shasum -a 256 -c SHA256SUMS` جایگزین کنید؛ نمایش منو بدون نصب نیز کار می‌کند. برای بررسی کامل، همهٔ فایل‌های فهرست باید موجود باشند. checksum تغییر فایل نسبت به فهرست را تشخیص می‌دهد؛ اگر مهاجم خود فهرست را هم عوض کرده باشد، اصالت را اثبات نمی‌کند. هر دو را از انتشار مورد اعتماد مالک بگیرید.

دستور `preview` فقط منو را نشان می‌دهد. اجرای بدون آرگومان منوی اصلی تعاملی را باز می‌کند. فایل بررسی‌نشده را مستقیماً به شل دارای دسترسی root ندهید.

## پورت‌های شبکه

| محل | دسترسی لازم |
|---|---|
| رابط عمومی خارج | پورت‌های TCP مربوط به HTTPS، معمولاً 443؛ پورت TCP 80 برای سایت HTTP نصب‌شده و چالش گواهی خودکار |
| loopback خارج | inbound اختصاصی برنامه و backend خصوصی WSS که نصاب انتخاب می‌کند؛ عمومی باز نشوند |
| رابط عمومی ایران | پورت‌های TCP ورودی انتخابی، مثلاً 21000 و 21001 در صورت آزادبودن |
| خروجی ایران | DNS، HTTPS بررسی‌های اولیه و پورت‌های HTTPS انتخابی دامنهٔ خارج |
| هر دو سرور | SSH فعلی و سرویس‌های ضروری دریافت بسته و هماهنگی ساعت |

پورت HTTPS خارج با پورت ورودی کاربر در ایران فرق دارد و لازم نیست شمارهٔ یکسانی داشته باشند. چند پورت ایران در یک تونل به همان مقصد برنامهٔ خارج می‌رسند. برای مقصد دیگری، تونل نام‌دار جدا با منابع جدا بسازید. اگر UFW از قبل فعال باشد، نصاب قواعد لازم TCP را اضافه می‌کند؛ UFW را فعال نمی‌کند و فایروال دیتاسنتر را تنظیم نمی‌کند. هر دو را بررسی کنید و قواعد فایروال مشترک را پاک نکنید.

## نصب خارج

ابتدا inbound برنامه و [DNS و گواهی](CLOUDFLARE.fa.md) را آماده کنید؛ سپس:

```bash
sudo bash GODOFTUN-V1.0.0.sh foreign
```

به پرسش‌ها به این ترتیب پاسخ دهید:

1. شناسه و نام نمایشی تونل را انتخاب کنید. شناسه ۱ تا ۴۸ حرف کوچک انگلیسی، رقم یا خط تیره دارد، با حرف یا رقم شروع می‌شود و دو خط تیرهٔ پیاپی نمی‌پذیرد. برای تونل تازه شناسهٔ تازه بگذارید.
2. MUX را روشن یا خاموش انتخاب کنید. مگر نیاز مشخصی دارید، از پیش‌فرض شروع کنید؛ [تنظیمات](CONFIGURATION.fa.md) را بخوانید.
3. دامنهٔ خارج با ابر نارنجی روشن و IPv4 واقعی سرور خارج را بدهید. پاسخ DNS عمومی باید کلودفلر باشد، نه IP خود سرور.
4. پورت‌های HTTPS را به ترتیب اولویت وارد کنید. برای شروع `443` کافی است؛ فقط پورت‌های مجاز کلودفلر پذیرفته می‌شوند.
5. پورت واقعی inbound اختصاصی را وارد کنید. نصاب اتصال به `127.0.0.1:PORT` را بررسی و برای backend خصوصی WSS پورت آزاد دیگری انتخاب می‌کند.
6. نمایهٔ TLS مرورگر و شدت padding را انتخاب کنید؛ پیش‌فرض padding برابر `0.22` است.
7. Let's Encrypt خودکار یا فایل گواهی و کلید موجود و CA محلی را انتخاب کنید. پیش از تأیید نصب، خطاهای بررسی اولیه را رفع کنید.

پس از راه‌اندازی، HTTPS محلی، ارتقای WebSocket با احراز هویت HMAC (نه تبادل کامل چالش‌ـ‌پاسخ V1) و مسیر CDN بررسی می‌شوند. کد اتصال خروجی محرمانه است و token مشترک را همراه اطلاعات اتصال دارد. Base64 رمزگذاری نیست؛ کد را در issue عمومی، تصویر یا فایل گیت‌هاب نگذارید.

## نصب ایران

همان نصاب بررسی‌شده را به ایران منتقل کنید؛ روش انتقال در صورت عدم دسترسی به گیت‌هاب در [مدیریت](OPERATIONS.fa.md) آمده است. سپس:

```bash
sudo bash GODOFTUN-V1.0.0.sh iran
```

1. بگویید آیا تونل دیگری روی سرور ثبت شده است. این پاسخ اجازهٔ جایگزینی تونل قبلی نیست.
2. کد اتصال خارج را بچسبانید. خالی‌گذاشتن این مرحله ورود دستی را باز می‌کند؛ برای نصب اول از کد استفاده کنید تا تنظیمات دو طرف اشتباه نشود.
3. هنگام درخواست، شناسه و نام محلی تونل و سپس IPv4 عمومی ایران را بدهید. دامنهٔ ایران خواسته نمی‌شود.
4. یک یا چند پورت آزاد کاربر را با ویرگول جدا کنید، مانند `21000,21001`.
5. سقف session و padding را انتخاب کنید. MUX و نوع انتقال از طرف جفت‌شده وارد می‌شوند.
6. ECH خاموش، ECH روشن سخت‌گیرانه یا ECH خاموش همراه Fragment آزمایشی ClientHello را انتخاب کنید. ECH و Fragment دو انتخاب جایگزین‌اند، نه یک حالت ترکیبی. [تنظیمات](CONFIGURATION.fa.md) را ببینید.
7. سهمیهٔ کلِ طول عمر تونل را بر حسب GB ده‌دهی مشخص کنید. `0` نامحدود است و آپلود و دانلود با هم شمرده می‌شوند.
8. پس از موفقیت بررسی‌ها تأیید کنید. نصاب sessionهای حامل را بررسی می‌کند، نه اطلاعات احراز هویت و انتقال واقعی برنامهٔ شما را.

اگر ورودی یا بررسی ناموفق بود، خطا را بخوانید و همان مرحله را اصلاح کنید. برای عبور از خطا اعتبارسنجی گواهی را خاموش نکنید و سراغ انتقال پشتیبانی‌نشده نروید.

## اتصال و تست کلاینت واقعی

در هر سرور شناسهٔ تونل خودش را پیدا کنید:

```bash
sudo godoftunctl list
sudo godoftunctl status TUNNEL_ID
sudo godoftunctl doctor TUNNEL_ID
```

به‌جای `TUNNEL_ID` شناسهٔ محلی فهرست‌شده را بگذارید. روی ایران، `sudo godoftunctl info TUNNEL_ID` اطلاعات کلاینت را نشان می‌دهد؛ خروجی را خصوصی بررسی کنید. آدرس اتصال کلاینت را IP ایران و پورت را ورودی اختصاصی خودش بگذارید؛ پروتکل، UUID/رمز و امنیت لایهٔ برنامه باید با inbound اختصاصی خارج مطابقت داشته باشد. اگر خود برنامه TLS دارد، شرط SNI و گواهی آن همچنان برقرار است. TLS برنامه با TLS بیرونی WSS یکی نیست.

پیش از ارائه به کاربران، روی مسیر واقعی خودتان همهٔ این موارد را بررسی کنید:

- کلاینت دارای احراز هویت از تک‌تک پورت‌های موردنظر آپلود و دانلود کند.
- اتصال هم‌زمان و انتقال فایل بزرگ‌تر بدون پاسخ ناقص کار کند.
- بعد از restart برنامه‌ریزی‌شده، اتصال تازه برقرار شود؛ ادامهٔ بدون وقفهٔ جریان‌های قبلی تضمین نیست.
- در صورت انتخاب ECH سخت‌گیرانه، پذیرش واقعی آن تأیید شود؛ Fragment جداگانه تست شود و مفیدبودنش فرض نشود.
- یک مشتری آزمایشی با سهمیهٔ کم به سقف برسد و درست مسدود شود؛ افزایش سهمیه مصرف ثبت‌شده را پاک نکند.
- عیب‌یابی، تمدید گواهی و اتصال پس از reboot سرور کار کنند. وضعیت `active` یا نمایش صفحهٔ وب عمومی به‌تنهایی کافی نیست.

نتایج تست را خصوصی نگه دارید و پیش از درخواست کمک اطلاعات محرمانه را حذف کنید. ادامهٔ راهنما در [مدیریت](OPERATIONS.fa.md)، [رفع خطا](TROUBLESHOOTING.fa.md) و [امنیت](SECURITY.fa.md) است.
